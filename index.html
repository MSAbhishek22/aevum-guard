A payment only happens if a rule you wrote allows it.

Aevum Guard is a guarded stablecoin wallet. The owner sets spending limits, hands out session keys that expire and can be taken back in an instant, and every action leaves a receipt in a hash-chained audit trail a third party can verify.

The problem

Stablecoin payments are easy to send — and hard to control.

Whoever holds the key can drain the wallet. An agent with a key can spend without limit. And after the fact, there is no receipt a third party can check. Aevum Guard puts three controls between the owner and the money.

01

One key, no limit

A wallet key is all-or-nothing. Hand it to a helper or an agent and you have handed over everything, with no way to say “only this much, only for this”.

02

Agents spend without a ceiling

An AI agent that can pay needs a key to pay with. Without caps, a wrong turn or a bad instruction can spend far past what the owner meant.

03

No proof after the fact

A transfer on its own says money moved. It does not say who allowed it, under which rule, or whether the rule was followed. That proof has to be built in.

How the guard works

Three controls. One rule: default-deny.

No limit means no payment. No live session means no delegated payment. Expired or revoked means the payment reverts. The owner writes the rules; the contract enforces them.

Control one

Spending limits

Per recipient, the owner sets three caps: per transaction, per day, per week — with per-tx ≤ per-day ≤ per-week enforced. Set all three to zero and that recipient is paused. Remove the limit and payments to them revert.

setLimit · removeLimit

Control two

Scoped session keys

A session key is a separate address with a narrow job: one category, one per-transaction cap, one expiry — at most seven days. The owner can revoke it in an instant, in the same block. A key can never raise its own cap.

grantSession · revokeSession

Control three

Hash-chained receipts

Every action — fund, limit, session, payment, withdrawal — appends a receipt. Each receipt hashes the one before it, so changing one breaks the chain. Anyone can re-check the whole chain with a single call.

verifyChain → (ok, failedIndex)

What pay() checks, in order

  1. Caller is the owner, or a live session keyelse NotOwnerOrSession · SessionRevoked · SessionExpired · ScopeMismatch
  2. Recipient has an active limitelse NoActiveLimit
  3. Amount within the per-transaction capelse OverPerTxCap
  4. Amount within the daily capelse OverDailyCap
  5. Amount within the weekly capelse OverWeeklyCap
  6. Guard holds enough to payelse InsufficientGuardBalance

Zero amounts revert with ZeroAmount. Each failed check names the exact rule it broke — the error is the explanation.

The contract

One contract. No external imports.

contracts/AevumGuard.sol — Solidity ^0.8.24. The Ownable, ReentrancyGuard and SafeERC20 behaviour is written inline, with the same revert names. Every state-changing function emits an audit event.

FunctionWhoWhat it does
fund(amount)ownerMove tUSD8 into the guard (approve first).
setLimit(recipient, perTx, perDay, perWeek, category)ownerSet a recipient’s caps; perTx ≤ perDay ≤ perWeek; all-zero pauses.
removeLimit(recipient)ownerDeactivate a limit — payments to them then revert (default-deny).
grantSession(key, scope, maxPerTx, expiresInSeconds)ownerRegister a scoped key, max 7-day expiry.
revokeSession(key)ownerInstant revoke, effective in the same block.
pay(recipient, amount, category)owner or live session keyThe guarded payment — runs every check above, then transfers and appends a receipt.
withdraw(amount, to)ownerEmergency withdrawal.
verifyChain(receiptHashes)anyoneRecompute the hash chain → (ok, failedIndex).
getLimit / getSession / getSpent / receiptHash(nonce)anyoneRead helpers for the UI and the audit trail.

Events, one per action: Funded, LimitSet, LimitRemoved, SessionGranted, SessionKeyRevoked, Payment, Withdrawn. One honest note from the build: the spec named both an error and an event SessionRevoked; Solidity forbids sharing one identifier, so the event is SessionKeyRevoked while the revert error keeps the spec name SessionRevoked.

Tests: 24/24 pass. Hardhat, local run, 17 Nov 2026 — caps and window rollover, session scope, expiry and revoke, owner-only guards, chain verify with tamper detection, a reentrancy attempt through a malicious token mock, and zero-amount rejection.

What is not in v1: multi-sig owners, ERC-8004 attestations, fiat ramps, recurring payments, cross-chain, upgrade proxies. Simplicity is the point — it keeps the contract auditable.
